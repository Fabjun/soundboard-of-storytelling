## Why

[P2](../README.md#principles): the app works without configuration; alternative behaviors become
options in Settings where they are cheap to build. Several decisions already wait for a Settings
screen (K12, the pad aspect ratio, PAD SIZE per board or app-wide, the backup reminder), and V1 had
one with six sub-screens — CONTROLS, APPEARANCE, VISUALS, KEYBINDING, DATA, DEVELOPER — plus ABOUT
([v1-v2-inventory.md §6](../v1-v2-inventory.md#6-settings)).

**S3 density (decided by Claude 2026-10-14, on the owner's instruction to decide on research; for review).** V1 had no density of the whole UI. It had two narrower ones: an icon density on the pad (how much a pad's icons grow with their number, a slider in the pad style panel) and a key map density (MINIMAL / NORMAL / DETAIL rows in the key map overlay). V3 lays a pad's icons out in a fixed grid where each icon fills its cell (`v3/src/components/PadIcons.tsx`), so the first has no counterpart; the second belongs to the key map overlay, which is Parked ([v1-v2-inventory.md §2](../v1-v2-inventory.md#2-controls--numpad)). A density of the whole UI (as Material Design or Gmail offer) would add a setting V1 never had (S12: as few settings as possible) and could not shrink controls below the 44 px touch target. So S3 is content width only; the key map density returns with the key map overlay.

Settings are stored as preferences in the `keyval` store (`v3/src/state/prefs.ts`), loaded before
the first render ([ADR-0062](../../architecture/0062-indexeddb-for-all-persistence.md)).
